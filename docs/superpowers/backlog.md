# ChronoLoop Frontend Rewrite — Backlog

Running list of parked/flagged items from the `CHRONOLOOP-frontend` rewrite. Not tracked via git history because this is a multi-phase project — check here first before assuming something was missed.

Each item: what, where it was noticed, why it was parked instead of fixed inline.

## From Phase 1 review

- [ ] **Avatar fallback gradient** — `TopBar.tsx`'s team-avatar cluster and user-avatar button (`src/components/layout/TopBar.tsx`) render a bare `<img>` with no `onError` handling. If an avatar file 404s or fails to load, the user sees a broken-image icon instead of an initials-on-gradient placeholder. Parked because a real fallback belongs with the `Avatar` design-system primitive (Phase 2), not bolted onto TopBar directly.

- [ ] **Test-ordering footgun in `App.test.tsx`** — `useThemeStore` (`src/store/themeStore.ts`) is a module-level Zustand singleton with no reset between tests. `themeStore.test.tsx` resets it explicitly in `beforeEach`, but `App.test.tsx` does not. Any future test in that file that clicks a theme toggle (via `Sidebar`) will leak `theme` state into later tests in the same run, order-dependent and hard to debug. No visible failure yet — flagged so the next person adding an App-level test doesn't get bitten.

- [ ] **README polish** — `CHRONOLOOP-frontend/README.md` covers structure/setup/extension points adequately but wasn't given a final editing pass (tone, redundant phrasing, missing "Testing" conventions section). Cosmetic, deferred rather than blocking Phase 1 sign-off.

- [ ] **Focus-ring / parity conflict** — `global.css`'s `:focus-visible` rule (`outline: 2px solid var(--accent-blue); outline-offset: 2px; border-radius: 4px;`) hardcodes a 4px radius, but several ported components (nav items, buttons) use their own radius (e.g. Sidebar `.navItem` at 8px). The focus ring's corner radius doesn't match the element it outlines on those components. Original `index.html` may have had the same mismatch (true parity) or may not have — not yet verified against the source. Needs a decision in Phase 2 when Button/other primitives formalize focus styling.

- [ ] **Avatar payload size** — `public/avatars/*.png` are 600KB–1MB each (5 files, ~4MB total) for images displayed at 28–36px. Never compressed/resized after being copied from the old repo. Deferred because it's asset pipeline work, not component work, and doesn't block Phase 1/2 functionality.

## From Phase 1 scaffold plan

- [ ] **"Integration" label inconsistency** — the sidebar nav label for the integrations page reads "Integration" (singular), matching `index.html`'s original text verbatim (see `Sidebar.tsx` `NAV_ITEMS`, and the original at `index.html:3001-3003`), while the route (`/integrations`), the page component (`IntegrationsPage`), and the rest of the design doc use "Integrations" (plural). Preserved as literal parity rather than silently "fixed." Needs a product-owner call: keep the original typo, or correct it now that it's been surfaced.

- [ ] **Theme not persisting on reload** — `themeStore.ts`'s `useThemeStore` has no `localStorage`/`persist` middleware, matching `index.html`'s original `setTheme()` (which also doesn't persist — always resets to `dark` on full page load). Intentional parity, not a bug, but flagged because it's the kind of thing a product owner may want changed now that it's a proper SPA. If persistence is wanted, it's a deliberate behavior change beyond parity — call it out explicitly before adding it.

## From Phase 3.1 (Dashboard)

- [ ] **Team grid email vs. member-detail email mismatch** — `src/data/mockDashboardTeam.ts`'s `gridEmail` (`'Joedoe@gmail.com'`, shown under every name in the Team Status grid) and `detailEmail` (each person's real address, shown in the Member Detail modal) come from two different hardcoded sources in the original (`index.html:3247,3252,3257,3262` vs. `index.html:6639-6644`). Preserved as literal parity rather than silently unified. Needs a product-owner call: keep both, or make the grid show the real per-person email now that it's centralized in one data file.

- [ ] **Three-dot project-row menu is always visible, not hover-revealed** — `CriticalProjectsPanel.module.css`'s `.threeDotBtn` omits the original's `opacity: 0` / `.row:hover { opacity: 1 }` treatment (`index.html:544,548`) so keyboard and touch users can reach it. Deliberate accessibility improvement over strict parity, not an oversight — flagged in case a visual diff review calls it out as a regression.

- [ ] **Decorative SVG triangle omitted from KPI delta rows** — `StatCard.tsx`'s delta row renders only the unicode arrow (▲/▼); the original also renders a small SVG triangle icon next to it (`index.html:3105`), visually redundant with the arrow. Explicitly reviewed and declined during Phase 3.1 (human ruling: skip) rather than silently dropped — noted here for completeness, not expected to be revisited unless a visual diff review disagrees.

- [ ] **`MemberDetailModal`'s card-width override uses `!important`** — `MemberDetailModal.module.css`'s `.card { max-width: 360px !important; }` fights `Modal.module.css`'s own `.card { max-width: 480px }` rather than composing cleanly. The established pattern for this exact kind of one-off primitive override (see the `Avatar` `style` prop added in Phase 3.1 Task 1) is an inline `style` passthrough rather than a CSS-Modules className fight — `Modal` doesn't currently accept a `style` prop. Fix: add `style?: CSSProperties` to `Modal`'s props (mirroring `Avatar`'s extension) and switch `MemberDetailModal` to use it, removing the `!important`.

- [ ] **"Select Project" dropdown option casing/sourcing is inconsistent** — `TeamStatusPanel.tsx`'s Select Project dropdown derives its first three options from `DASHBOARD_CRITICAL_PROJECTS` (whose title is `'Web 3 app for Fxtrade'`, lowercase "app" — correct for the Critical Projects row it's sourced from) while the original's dropdown item reads `Web 3 App for Fxtrade` (`index.html:5476`, capital "App"). Separately, the 4th option ("ChronoLoop Launch") is bolted on as a one-off item outside the `.map()` rather than living in the same list. A dedicated `PROJECT_OPTIONS` constant (distinct from `DASHBOARD_CRITICAL_PROJECTS`, which should stay scoped to the Critical Projects panel) would fix both the casing and the asymmetry. This is the same underlying gap as the "full project list has no shared data source yet" issue noted during Task 6 — likely worth resolving once the Projects page (Phase 3.2) establishes a real shared project list.

- [ ] **`TeamStatusPanel` tracks `project` and `projectLabel` as two parallel states** — they're only ever written together (in `selectProject`), so a single `selectedProject: string | null` would express the same thing with less surface area for the two to drift. Cosmetic; not a bug today.

- [ ] **`DashboardHeader`'s CSV export leaks a timer and a blob URL** — the 1600ms `setTimeout` in `handleExport` isn't cleared on unmount (it still fires and triggers a download after navigating away), and `URL.createObjectURL` is never paired with `revokeObjectURL`. No security concern today since the CSV is a hardcoded string literal with no user input — but flagging now because once this gets wired to real task data (user-entered titles, project names), CSV-injection escaping (`=`, `+`, `-`, `@`-prefixed cells) will need to be added at the same time.

- [ ] **Filter dropdown's checkboxes may not be keyboard-reachable inside a Radix `DropdownMenu`** — `DashboardHeader.tsx`'s Filter panel puts raw `<input type="checkbox">` elements and Clear/Apply buttons inside `Dropdown.Content` (Radix `DropdownMenu.Content`), which manages roving focus across `MenuItem`s and closes on Tab by default. Never interactively/browser-verified (Phase 3.1 had no browser available in its execution environment) — if this holds, the filter panel is effectively mouse-only. If confirmed, `DropdownMenu.CheckboxItem` or swapping the whole panel to a `Popover`-based primitive would be the correct fix.

- [ ] **`.weekBtn`/`.roleBtn` CSS rule block is duplicated across 3 files** — near-identical rules appear in `CriticalProjectsPanel.module.css`, `CalendarWidget.module.css`, and twice within `TeamStatusPanel.module.css` (role dropdown + select-project dropdown). The original had one shared `.dropdown-btn` class. Consider a shared CSS module or a small `ui/` primitive once a third or fourth page needs the same "small dropdown trigger chip" look.

- [ ] **Phase 3.1 was never interactively verified in a real browser** — every task's automated test suite passes (95/95 at Phase 3.1's close) and static wiring was checked, but no environment with a browser was available during implementation to click through KPI animations, all four modals, calendar pill positioning, or the toast-emitting dropdowns. Recommended: do one manual `pnpm dev` pass through the Dashboard page before/alongside starting Phase 3.2, to catch anything automated tests can't (visual glitches, animation timing feel, real click-through flows).

- [ ] **Global Constraints' "never modify the old repo" rule needs a carve-out for `docs/`** — Phase 3.1's plan stated "Never modify `C:\Users\HP\Downloads\Chronoloop dashboard\`" as a blanket rule, but its own Task 9 correctly required editing `docs/superpowers/backlog.md` in that same repo (this file). The intent was always "don't touch `index.html`/`design.md`/the old app," not "don't touch the planning docs that happen to live alongside it." Future phase plans should word this constraint as "never modify the old app itself (`index.html`, assets, `design.md`) — `docs/` in that repo is the shared planning-docs location and is fair game."
